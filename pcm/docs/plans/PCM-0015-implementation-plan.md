## Smallest useful rollout (scope decision)

PCM should stay a lightweight, Git-centered continuity tool—not become a required knowledge-graph platform. This plan is a menu of separately authorized slices, not one upgrade commitment. The first proof path is deliberately limited:

1. **Make adoption instructions true:** unify package-version reporting, test what a newly initialized repository actually receives, and install/run a built artifact outside the source checkout (S1). This repairs the current trust gap; it does not publish a release.
2. **Make the existing checkpoint safe to retry:** one stable request ID produces one durable event even across interrupted push/retry (S2). Do not redesign recovery or all project state as part of this slice.
3. **Test the real continuity failure cheaply:** add explicit document inventory/search for a declared scope, then one task-sized context pack and an independently fresh-session trial (S7–S8). Keep old files and existing handoff usable; compare against baseline and stop if benefit is not demonstrated or upkeep breaches the measured cost budget.

S3–S6 are prerequisites only where a chosen implementation needs them, and must each be separately opened and accepted. Assertion/freshness tracking and task-ownership automation (S9–S10) are not part of the minimum path; defer them unless the S7–S8 trial reveals a specific failure they solve. Publishing to PyPI, an npm launcher/native Node implementation, host hooks, PROV export, and distributed locking are separate projects triggered by demonstrated consumers—not hidden substeps. PCM remains useful without them.

Routine delivery should remain: run relevant product checks, make one checkpoint call that records evidence/next action and pushes, then let the PR's required CI gate automatic merge. Full inventory and context-pack generation belong at meaningful session handoff, not every edit. **Current cost warning:** `.github/workflows/ci.yml` runs the full quality, Python 3.11/3.12 test, and package jobs on both every push and every pull request. A task branch that is pushed and then opened as a PR therefore repeats the full workflow; repeated checkpoint pushes repeat it again. The first adoption/CI slice should keep the full merge gate but avoid that redundant branch-push-plus-PR execution (for example, lightweight branch-push checks and the full matrix on PR events), with a deterministic workflow-trigger regression check. Do not call the pipeline efficient until this is verified. This target design is **not a claim that current behavior already has these properties**. CI only blocks merge when branch rules actually require it; repository onboarding can require use of PCM's documented path, while an agent host must cooperate to enforce worker lifecycle or behavior before merge.

## Enforcement and distribution boundaries

| Surface | What it can enforce | What it cannot establish |
|---|---|---|
| PCM command in a repository | Reject malformed/unsupported records, mismatched generated blocks, broken references, conflicting operation IDs, unsafe migrations, and local owner conflicts before its own writes. | Stop direct file edits, prove prose true, prove an agent read/understood a document, find semantic duplicates perfectly, or control an unintegrated host. |
| Required CI | Check the submitted tree, pinned validator/version, inventory coverage within declared scope, deterministic views, and recorded evidence references. | Observe every session/branch or prevent work before submission. GitHub merge blocking requires separately configured protection/rules and permissions; workflow YAML alone is insufficient. See [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). |
| Package manager | Install a chosen executable and apply its interpreter/dependency constraints in the managed installation path. | Migrate arbitrary repositories, make all agents invoke PCM, close workers, or guarantee future Python/Node compatibility. |
| Optional host/coordination adapter | Intercept supported start/write/stop hooks, observe worker handles, perform cleanup, or serialize claims through an atomic authority. | Control bypassing clients or unsupported hosts. GitHub issue text is not automatically an atomic lock. No such adapter is demonstrated here. |

**External:** PyPA defines `requires-python` and executable entry points ([pyproject guide](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)). Pip supports source/VCS/wheel installation and explicit upgrades; editable installs expose source changes but metadata/entry-point changes can require reinstall ([pip install](https://pip.pypa.io/en/stable/cli/pip_install/), [local installs](https://pip.pypa.io/en/stable/topics/local-project-installs/)). Uv offers cached isolated `uvx`, persistent `uv tool install`, and explicit `uv tool upgrade`; upgrades respect installation constraints ([concepts](https://docs.astral.sh/uv/concepts/tools/), [tools guide](https://docs.astral.sh/uv/guides/tools/)). None of this updates PCM-managed target files by itself.

**Recommendation:** preserve documented source installation for development in the existing root environment. Establish wheel/sdist installation tests before advertising public installation. For consumers, document an exact source revision or verified wheel initially; after a separately approved publication, offer pinned `project-continuity==<released-version>` through pip, or `uvx --from project-continuity==<released-version> continuity ...`. The placeholder is not an available release claim. Persistent uv tooling is an optional host installation choice, not a per-task environment. Record installed version/source; avoid floating `latest` in CI and checkpoint commands. A tool upgrade and a repository migration are separate explicit actions.

Keep Python 3.11 as the floor for these slices. **External:** Python's published schedule lists 3.11 security support through October 2027 and 3.14 as stable at the evidence date ([Python version status](https://devguide.python.org/versions/)). **Recommendation:** test 3.11–3.14 on Linux, add Windows install/CLI smoke coverage, and treat 3.15 prerelease checks as advisory until release and verification. Recheck the schedule when implementing. No speculative upper bound or automatic floor increase; review the floor near end of support, announce a separately scoped compatibility change, and retain the old compatible package line where practical. `>=3.11` is an installation declaration, not evidence that every future interpreter works.

## One authoritative state, small derived views

**Recommendation:** keep one logical machine-readable state with one owner for each fact; do not introduce a second writable snapshot of existing state. It need not be one enormous file. Existing `continuity:*` JSON markers own PROJECT/CURRENT/task/checkpoint structured fields. A proposed optional `.continuity/memory.json` owns only new document records and, later, assertion records; `.continuity/config.json` continues to own configuration. References connect them by stable IDs. A machine `state --json` view may join these records, but is generated and never edited or imported back as authority. No independently writable `state.yaml`, index copy, or tracker mirror.

For each supported record, render its structured facts into a marked human-readable block from the authoritative JSON. A `render --check` compares bytes without writing; `render` changes only owned blocks. Keep PROJECT's domain prose and task scope/acceptance explanations outside generated blocks unless explicitly mapped. Existing checkpoint JSON/human entries are immutable historical records; generate/check newly created entries, report old disagreements, and do not rewrite history. New render contracts identify their version and source hash; timestamps come from recorded events, never render time. Checkpoint task `next_action` and its generated summary update together; CURRENT changes only when program state changes. Preserve the evidence history of earlier next actions.

Migration must map every structured field, identify conflicting marker/prose values for review, and preserve unmapped prose byte-for-byte. Repeated markers or ambiguous ownership fail before mutation. This is narrower than converting all project prose to a new manifest. A future single-file format would be an incompatible migration requiring its own task, not a prerequisite for discovery.

**Standard:** [JSON Schema 2020-12](https://json-schema.org/draft/2020-12) specifies structural contracts. **Recommendation:** use only explicitly supported keywords initially; fail on unsupported schema features instead of silently ignoring them. A standards-compliant validator dependency is a separate decision if new requirements exceed the subset. Bind CI to approved schema digests so editing a target schema cannot silently weaken a gate.

## Versions, adoption, and command retry contracts

**Recommendation:** keep independent CLI/package, protocol, schema/render format, and template revision identities. One package-version source must feed installed metadata and diagnostics. A package release publishes a compatibility table: protocols it reads/writes, optional capability versions, migration IDs, and template digests. Unknown newer protocol/capability versions get an actionable read-only audit and refusal to mutate, not guessed compatibility.

[SemVer](https://semver.org/spec/v2.0.0.html) is an established versioning specification, but 0.x alone promises no stability. Apply PCM's explicit compatibility policy: fixes use package patches, additive commands use minors, breaks require an announced boundary. Optional memory capability adoption must not silently change the meaning of `0.1.0-draft` core validation. An opted-in repository pins a capable CLI and CI gate; old CLI success establishes only old-core validity. Promotion to mandatory state is an incompatible protocol change coordinated with queued PCM-0007, with exact release numbers decided there. Validate preserved historical records against their declared supported schema/version and explicit transition rules; never blindly rewrite every historical protocol label to match CURRENT.

Proposed `audit` is offline/read-only by default and reports installed tool, declared protocol/capabilities, schema/template drift, and applicable bundled migrations. Remote update checks are explicit. Proposed `upgrade --plan` produces a deterministic source/target/digest-bound diff; `--apply` requires those same preconditions. Update only owned files/blocks against their known base: three-way merge safe changes, report overlaps and unknown fields, refuse destructive transformations without explicit authorization. Stage and validate the whole transaction before replacement; retain a journal for crash recovery. No automatic commit/push/merge from migration; normal reviewed delivery remains separate. Rollback is a reviewed Git revert or saved preimage restoration with matching hashes, never a reset of user changes.

| Operation | Proposed repeat-run invariant |
|---|---|
| `validate`, `audit`, `find`, `inventory --check`, `render --check` | No writes; same inputs and explicit evaluation time give identical ordered results/exit status. Inventory scan proposes candidates; registration is explicit. |
| `init` | Same initial inputs: no byte changes; conflicting existing project state: refuse without changes. Reinitialization is not migration. |
| `task new` | Remains intentional allocation without a key. Optional request ID makes retries return the original task; same ID/different payload conflicts. A repeated goal is not sufficient to infer identity. |
| `checkpoint`, recovery reconciliation | Persist event/request ID plus canonical payload digest before side effects. Same ID/payload returns or completes the original event; different payload conflicts. A new event may have identical prose. Preserve the original timestamp/source revision on retry. |
| publication | Track prepared → recorded → committed → pushed; retry after a crash discovers the recorded event/commit and retries only missing delivery. Check the remote contains the intended commit, including successful push with lost response; never duplicate the event or force-push divergence. An offline pending event is explicitly incomplete delivery. |
| register/rename document, ownership transition | Same stable ID and expected prior revision is a no-op when already applied. Different contents or owner require an explicit transition; concurrent edits conflict. |
| render, pack, handoff | Fixed source manifest, task selection, renderer version, and budget produce identical bytes, no new timestamp or commit. |
| upgrade | Same migration ID/source/target already applied: verify and no-op; stale plan or changed managed preimage: refuse without partial writes. |

Checkpoint transaction/recovery is real work: split normal publication retries from receipt reconciliation. Do not silently broaden the current recovery exception into permission for new clones, worktrees, environments, or storage repair.

## Discovery, evidence, ownership, and packs

**Recommendation — discovery:** inventory tracked documents in explicit configured scopes (initially project/agent/handoff/spec, tasks, checkpoints, docs and artifacts); exclude fixtures, vendored/generated files and packs by declared rules. Each document has stable ID, current path, title/purpose, topics/aliases, task IDs, status, related IDs, explicit `supersedes` links, and source event/revision when known. Pre-existing records may say origin unknown. Hashes bind content, not identity: edits/renames retain IDs; deleted historical records retain commit/path tombstones. Validate unique IDs, in-root paths, resolvable links, and acyclic supersession; derive backlinks rather than maintain two directions.

`find` searches title/topics/aliases/task links and document text deterministically, returns matching snippets and one-hop neighbors with reasons, and follows supersession in both directions. Include archived/superseded hits with status; never hide old decisions merely because CURRENT omitted them. If the index is stale/incomplete, expose the gap and fall back to scoped repository text search. Before creating a document, run lookup and inspect likely hits; same-ID/path duplicates can be rejected, semantic similarity is only a warning requiring judgment. Store lookup evidence on document creation, not every checkpoint. CI coverage starts advisory during backfill and becomes required only for declared scopes after coverage review. This cannot prove an unseen differently worded duplicate does not exist.

**Recommendation — assertions:** distinguish factual assertions from task ownership claims. A later optional assertion record has ID, statement, scope, origin class (user requirement, observation, external source, model proposal, inference), author/reviewer, evidence references, and independent assessment (supported/unknown/contradicted), freshness (current/stale/unknown), and supersession. Do not equate a requirement with an observed fact or use one overloaded status enum. Evidence includes inspected commit/blob, command and environment, exit/result, artifact digest, checked time and dependency scope; lines are locators, hashes/revisions anchor identity. Historical tests remain historical observations. Relevant file/dependency changes make present-tense applicability stale; unrelated changes need not. A failing mapped test records counterevidence without declaring every linked assertion false. External evidence may have a review deadline; offline checks report overdue/unknown rather than fetch or fabricate current truth. Deterministic checks take `--as-of`, and cannot verify semantic relevance automatically.

**Recommendation — ownership:** retain serial work in the canonical checkout. Initially task `owner` is the authoritative assignment, not a distributed lock. Later record session identity, branch/base, expected prior ownership revision, claim/release/handoff events, and takeover reason in task metadata/history. A local lock plus compare-and-swap protects cooperating local commands; CI checks valid transitions and at most one active assignment in the submitted state. Completed/cancelled tasks require release. Do not infer abandonment from elapsed time or automatic lease expiry. Cross-host exclusivity needs an explicitly scoped atomic coordination adapter and fencing; disconnected actors remain unprotected. Defer leases and keep GitHub/Beads mirror tasks separate.

**Standard:** [PROV-O](https://www.w3.org/TR/prov-o/) models/interchanges provenance using entities, activities, agents and relations; [SHACL](https://www.w3.org/TR/shacl/) constrains RDF graphs. Neither certifies truth or provides live locks. **Recommendation:** retain the existing [research Turtle](../research/PCM-0015-provenance.ttl) as source evidence, but use JSON/markers natively for runtime state. Only add a deterministic PROV-O export when a consumer exists: document/evidence revisions → entities, checkpoint/test/migration → activities, people/sessions → agents, with derivation/attribution relations. PCM assessment/freshness terms remain explicitly local extensions. Native RDF adds parsing, ontology/shape and migration costs without a demonstrated current benefit.

**Recommendation — task pack:** select required policy/project context, task scope/acceptance, latest checkpoint, exact next action, relevant document hits/neighbors, unresolved contradictions and required checks. Link older histories rather than concatenate them. Emit inclusion reasons, omitted-source list, source hashes/revision, tool/render version and a default 6,000-token-equivalent budget with deterministic byte accounting. Never silently omit mandatory scope or blockers; exceed budget only with an explicit report/override. Use a committed source revision; dirty previews must be labeled and hash actual bytes. A committed pack describes its source commit, not the commit that later contains the pack: avoid self-referential HEAD/hash regeneration loops. Packs remain disposable; generate at takeover/major handoff or on demand, not at every checkpoint.

**Inference:** explicit lookup and smaller packs may reduce forgotten documents and duplication. [Lost in the Middle](https://arxiv.org/abs/2307.03172) reports context-position effects in evaluated models/tasks; it does not prove PCM efficacy or universal context-rot prevention. Test the behavior below before claiming it works.

## Routine cost budget

**Recommendation:** ordinary checkpoints remain three user-visible stages: (1) relevant product checks and commit, (2) one checkpoint invocation recording evidence and next action while validating changed records/links and regenerating only affected blocks, (3) publish result or explicit pending-delivery report. CI runs the full merge gate. No routine full history scan, external-source polling, RDF export, pack generation, package upgrade, model summarization, all-project test run, or agent creation. Existing full validation remains the safe fallback until incremental checks are proven equivalent on affected invariants.

At major handoff/task rotation: audit inventory changes, review relevant stale assertions, generate the task pack, verify remote delivery, release/transfer ownership, capture worker results and close them through the host. At release/migration: full inventory, schema/view checks, compatibility/install tests, and fresh-session evaluation. Rotation follows a completed bounded slice, context difficulty, or user choice; do not invent a universal turn limit.

Proposed performance gate: fixed fixture with 1,000 documents/100 tasks; 20 repeated runs on recorded hardware; local checkpoint bookkeeping p95 ≤2 seconds and ≤1 second added over baseline, excluding product tests/Git network/CI. Measure those excluded times separately. Routine entry target ≤250 words plus evidence links. These are acceptance budgets to measure, not current performance claims. If exceeded, stop adding scope and investigate changed-record work/caching, with rebuildable caches only.

## Deterministic and truly fresh-session acceptance

**Recommendation — deterministic suite:** use fixed clocks, request IDs, Git revisions and synthetic local remotes; no network or LLM in required unit tests. Assert file bytes, exit codes, event counts, exact scoped changes and remote commit reachability, not only phrases. Include unsupported-version refusal, custom schema weakening, path traversal/symlink escape, Unicode/case path handling, interrupted transactions, dirty/index preservation, source/pack tampering, malformed evidence and old-format fixtures. Metamorphic tests repeat operations, rename documents, reorder input records, change only unrelated files, and compare outcomes.
