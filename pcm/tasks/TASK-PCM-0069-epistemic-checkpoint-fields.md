## Human outcome

A fresh session can read a checkpoint and tell, from the record rather than from prose tone, whether an entry reports something the writer observed or something it inferred, what earlier request it supersedes, and what date the claim covers — and the digest still proves nobody edited those fields after the fact.

## Scope and boundaries

- In scope: three optional marker fields, the CLI flags that write them, the schema extension, and the digest rule that keeps old records verifying.
- Out of scope: requiring evidence links at validation time, adopter ticket placement, and the parked/aging policy — all still open questions on #144 with no recorded owner answer.
- **Adopter schema copies are snapshots, and that is a real forward dependency.** `load_schema` (src/continuity/cli.py:325-340) reads the *target checkout's* `.continuity/schema_dir` copy first and only falls back to the built-in; `continuity init` materializes that copy into the adopter's tree, so it freezes whichever schema the build had at their init time. Verified experiment: with a complete baseline marker, an unextended schema reports `$: unexpected key 'evidence_class'` / `'supersedes'` / `'as_of'`, the extended copy accepts all three, and an `evidence_class` value outside the enum reports `$.evidence_class: expected one of ['observed', 'inferred']`; editing only the checkout's copy changed what `load_schema` returned, which proves the checkout copy governs. Consequence: once PCM's `checkpoint` command writes these fields, an existing adopter validating a PCM-written marker with its older in-tree schema gets `unexpected key` errors — PCM's own repository stays green because its copy is updated in the same commit, while the adopter's CI is not. Newly initialized checkouts are covered by extending `BUILTIN_SCHEMAS` in the same commit (criterion 1); only already-adopted trees need the #107/#108 refresh path.
- Two claims this projection previously carried are **withdrawn as unproven, and the correction is recorded here rather than silently overwritten**: (i) "`templates/v1/schemas/checkpoint.schema.json` exists and has drifted" — there is no `templates/v1/schemas/` directory at all (`templates/v1/` contains only `minimal/` and `software/`), so new targets receive their schemas from `BUILTIN_SCHEMAS` at init; (ii) "`validate_schema({"request_id": "probe"}, "checkpoint")` returned `[]`, proving a drift path" — that call passes a string where a loaded schema dict belongs and raises `AttributeError: 'str' object has no attribute 'get'`, so it proved nothing about schemas; the `[]` I first read out of it was an artifact of how I captured output. `schemas/v1/checkpoint.schema.json` and `BUILTIN_SCHEMAS["checkpoint"]` compare equal on both `required` and `properties` today.
