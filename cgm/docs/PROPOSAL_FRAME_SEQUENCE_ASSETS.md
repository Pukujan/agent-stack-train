# A frame-sequence role for animated narrative assets

Status: proposal, not shipped. Tracker issue: [#40](https://github.com/Pukujan/content-generation-modules/issues/40).
This document changes no module, no schema, and no validator today. It records
a method that worked in an adopter repository and proposes
what CGM would have to check so future adopters do not invent their own bypass.

## The problem we observed

CGM's image-generation contract governs single narrative assets. The validator
(`check_narrative_assets` in `scripts/validate_content_system.py`) requires a
narrative-role asset to record `path`, `role`, `orientation`, `dimensions`,
`text_policy`, `prompt_recipe`, `exact_title`, `exact_subtitle`, `alt_text`,
`usage`, `crop_behavior`, `rejection_conditions`, `review_decision`,
`provider`, `prompt_record`, and `hash`. It also restricts the file suffix to
`.png`, `.jpg`, `.jpeg`, or `.webp`.

There is no role, no schema, and no validator for a sequence of frames that
must stay consistent with each other. In `Pukujan/stylish-profile` (commit
`e2af2da2d3ff1641d0aa169255dc83ace998fa0e`, 2026-10-01), two animated assets
were produced anyway:

- `assets/profile/anim/Reusable Blocks.gif` — 720x720, 5 frames
- `assets/profile/anim/One Push Many Pipelines.gif` — 720x720, 5 frames

The adopter gave them `role: "motion"`. That string matches none of the
narrative role markers (`hero`, `problem`, `supporting`, `evidence`, `story`,
`social`), so the validator skips the frames entirely. They were recorded with
full field sets by hand, which is good practice, but nothing enforced it. An
adopter that recorded less would pass. The `.gif` suffix would itself fail the
current narrative suffix rule, so the only way an animated asset can exist
today under a checked role is to dodge the role check. That is a hole, not a
design.

## The method that worked

We produced both GIFs with the existing built-in image-generation workflow.
Five steps, in order:

1. Frame 1 was generated from a full text prompt.
2. Frames 2 through N were generated by passing the previous frame as
   `input[]` (image-to-image), keeping the same `subject`, `scene`,
   `composition`, `lighting`, `style`, and `text` fields, and adding exactly
   one entry in `changes[]` describing the single thing that moves. Re-prompting
   from text alone drifted the style, palette, and geometry between frames; the
   chained generation is what kept them consistent.
3. Every prompt carried an explicit negative text clause naming every surface
   that must not gain a wordmark: "no logo, no wordmark, no brand mark, no
   labels, no captions, no signage, no text on tools, boxes, screens or
   blocks".
4. Frames were assembled to a GIF with Pillow. The final frame was quantized
   with `Image.quantize(colors=64, method=Image.MEDIANCUT)` to build one shared
   palette, then every frame was quantized against that palette with
   `dither=Image.NONE`, and the file was saved with `save_all=True`,
   `append_images=...`, `duration=[...]`, `loop=0`, `optimize=False`,
   `disposal=2`. The shared palette is what stops inter-frame colour flicker;
   per-frame palettes flicker because each frame picks its own 64 colours.
5. Each frame was reviewed by vision separately for stray text before
   assembly.

## The rejected attempt, recorded

Without the negative clause in step 3, the renderer invented a two-word logo
block in a corner. This was observed on generated frames, not theorised, and
the affected frames were rejected. That is why the clause is a required part of
the prompt contract rather than advice.

## GIF and not APNG, measured on GitHub

GitHub's Markdown renderer attaches `data-animated-image` to a rendered `.gif`
image. It does not attach it to `.apng`, `.png`, `.webp`, or `.jpg`. An APNG
therefore renders as a single frozen frame in Markdown. Measured on GitHub on
2026-10-01 by pushing a README containing both formats and inspecting the
rendered DOM. Full inline media results are recorded in
[`GITHUB_INLINE_MEDIA.md`](GITHUB_INLINE_MEDIA.md).

## Proposed contract shape

A new sequence role (working name `motion`, promoted from a bypass string to a
checked marker) governed by its own required fields, per sequence rather than
per file:

- `sequence`: `frame_count`, `frame_order` (for a ping-pong loop see
  [`PROPOSAL_MOVING_HERO.md`](PROPOSAL_MOVING_HERO.md)), `duration_ms` per
  frame, `loop: true`;
- `frames[]`: one entry per committed frame image with `index`, `path`, `hash`,
  `prompt_record`, and for frames 2..N an `input` naming the previous frame
  file plus a `changes` array of exactly one entry, while `subject`, `scene`,
  `composition`, `lighting`, `style`, and `text` must be declared once for the
  sequence and repeated unchanged;
- `assembly`: `tool`, `palette_source` (the frame that defines the shared
  palette), `colors`, `palette_method`, `dither: none`, `disposal: 2`,
  `loop: 0`, and the final delivered file `path` and `hash`;
- `negative_text_clause`: the verbatim no-text instruction, required on every
  frame prompt;
- the existing per-asset fields (`orientation`, `dimensions`, `text_policy`,
  `alt_text`, `usage`, `crop_behavior`, `rejection_conditions`,
  `review_decision`, `provider`) apply to the delivered sequence file, with
  `dimensions` and `frame_count` describing frames, not the container.

## Proposed validator rules

These are the checks that would make `role: "motion"` as a dodge unnecessary,
because the checked motion role then accepts what a GIF actually is:

1. `motion` joins the checked role markers and gets the sequence field set
   above instead of the single-asset field set.
2. The delivered container suffix is validated against an allow-list for
   sequences (`.gif` for GitHub-rendered animation), and the container hash is
   verified against the committed bytes.
3. Frame 2..N entries MUST record an `input` that names the committed file of
   the previous frame, and exactly one `changes` entry. Zero or two or more is
   an error.
4. The declared `negative_text_clause` MUST appear (literal substring) in every
   recorded frame prompt.
5. `assembly` MUST declare one shared palette (`palette_source` set,
   `dither: none`, `disposal: 2`, `loop: 0`) and a `duration_ms` array whose
   length equals `frame_count`.
6. `review_decision` MUST record that every frame was checked for stray text
   before assembly; a review of only the final frame fails.
7. The APNG/webp containers stay rejected for Markdown placement, with a pointer
   to the measured `data-animated-image` finding.

## Boundaries

- Nothing here is implemented. No schema, validator, or module file is changed
  by this proposal.
- The chained-generation behaviour is provider behaviour (the built-in
  image-generation workflow that accepts `input[]` and `changes[]`). A different
  provider would need its own equivalent record; the contract above records
  intent, not a guarantee.
- The two stylish-profile GIFs are evidence that the method works, not proof
  that any future provider keeps frames consistent the same way.

## Acceptance criteria for the eventual implementation

1. `schemas/` gains a sequence shape with the fields above and a validator
   enforces rules 1 through 7 fail-closed.
2. `modules/image-generation/SKILL.md` and `docs/IMAGE_GUIDE.md` document the
   frame-chaining workflow, the required negative clause, the rejected-attempt
   record, and the shared-palette assembly step.
3. A unit test rejects: a frame-2 entry with no `input`, a `changes` array of
   two entries, a missing negative clause, a per-frame palette (`dither` set or
   no `palette_source`), and a duration array whose length differs from the
   frame count.
4. An adapter example (the stylish-profile shape) passes with `role: "motion"`
   and needs no field-level bypass.
5. A `human-output-naming` legend entry covers animated basenames.
